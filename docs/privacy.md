# Privacy

Inquisitor collects aggregate timing features, not typed content or pointer targets.

## What is collected

- Keyboard timing statistics per rolling window (press counts, hold variability, overlap)
- Mouse motion and click timing aggregates. The Windows agent always sends them with the keyboard
  aggregates (schema v4); the browser arcade's mouse collection remains a separate opt-in
- Account email and device metadata needed for pairing and authorization

## Feature window fields

Every window that leaves the collector matches one of the schemas in
[`shared/`](../shared). Schemas reject additional properties, so these are the
only fields a window can carry.

| Field | Contents |
| --- | --- |
| `schema_version` | 1, 2, 3, or 4. The Windows agent sends only 4 |
| `device_id`, `session_id` | Opaque identifiers issued at pairing and per collection session |
| `sequence` | Window counter within a session |
| `mode` | `enrollment` or `monitoring` |
| `started_at`, `duration_ms` | Window start time and length |
| `features` (v1, v2) | `key_count`, `presses_per_second`, `hold_mean_ms`, `hold_std_ms`, `press_interval_mean_ms`, `press_interval_std_ms`, `press_interval_p90_ms`, `press_overlap_fraction`, `burst_count`, `pause_count`, `pause_fraction` |
| `mouse_features` (v2) | `move_count`, `speed_mean_px_s`, `speed_std_px_s`, `acceleration_mean_px_s2`, `acceleration_std_px_s2`, `turn_angle_mean_rad`, `click_count`, `click_interval_mean_ms`, `click_interval_std_ms` |
| `features` (v3) | `key_count`, `hold_sample_count`, `hold_mean_ms`, `hold_std_ms`, `press_interval_mean_ms`, `press_interval_std_ms` |
| `features` (v4) | The v3 fields plus `mouse_sample_count`, `mouse_speed_mean_counts_s`, `mouse_speed_std_counts_s`, `mouse_turn_mean_rad`, `mouse_turn_std_rad`, `mouse_path_straightness`, `mouse_click_count`, `mouse_click_interval_mean_ms`, `mouse_click_interval_std_ms` |

Mouse values are speeds, angles, counts, and intervals. None of them is a position.

## What is not collected

- Key identities, typed characters, or ordered key sequences
- Absolute pointer coordinates, click targets, or window titles
- Raw event logs outside transient in-memory pairing

## Storage and retention

Enrollment windows support model training. Monitoring windows, inference results, and
alerts follow the configured retention period on the ML service. `DELETE /me/data` on the
ML service and the local arcade removes an account's windows, results, alerts, and models.
On the hosted service, "Delete my data" on the setup page calls `DELETE /api/me/data`, which
removes the same data from the ML service and Atlas and revokes every paired agent. Hosted
Atlas monitoring rows have no automatic retention purge yet.

## Remote processing

Training and inference run on the designated remote ML host. Enrollment windows leave the
user's device only after explicit onboarding. Credentials for that host never ship in the
client binary.

## Automated privacy scanning

[`scripts/scan_privacy_payloads.py`](../scripts/scan_privacy_payloads.py) checks supplied JSON,
JSONL, and JSON audit log records. It rejects:

- Feature windows that fail `backend.ml.model.validate_window`, including unknown properties,
  invalid numeric types, non-finite features, and the validator's plausibility limits
- Persisted document keys outside the fields inserted by `Frontend/hosted.py` into `windows`
  and `monitoring_windows`, and result keys outside the scoring response metadata
- Audit keys outside the metadata emitted by `hosted.audit_event`, including nested values;
  captured audit strings are decoded as JSON before checking
- Lists containing objects, lists, or numbers outside the explicit capture collection fields
- String values containing `http://` or `https://`

The Backend GitHub Actions workflow scans these inputs:

- [`shared/fixtures/tray-capture.v4.json`](../shared/fixtures/tray-capture.v4.json)
- [`sample-data/windows.jsonl`](../sample-data/windows.jsonl)
- A temporary JSON file freshly generated by
  [`scripts/capture_agent_link_artifacts.py`](../scripts/capture_agent_link_artifacts.py),
  containing the upload request, returned enrollment/monitoring payloads, persisted documents,
  and decoded audit records from the in-process agent link test server

This checks field names, window schemas, selected list shapes, and URL markers in those inputs.
It does not establish that arbitrary text in an allowed string field is harmless, or that other
routes, logs, storage, or runtime traffic contain no prohibited data. Unit tests in
[`tests/test_privacy_scan.py`](../tests/test_privacy_scan.py) cover known bypass cases.

## Agent link capture (local, not production HTTPS)

To inspect what the hosted agent routes accept and persist without a deployed site, use the
in-process capture helper against [`scripts/agent_link_test_server.py`](../scripts/agent_link_test_server.py):

```text
uv run --no-project --python 3.13 --with-requirements Frontend/requirements.txt ^
  --with "mongomock>=4.3,<5" python scripts/capture_agent_link_artifacts.py "path-to-temporary-capture.json"
uv run --project backend python scripts/scan_privacy_payloads.py "path-to-temporary-capture.json"
```

What this exercises:

- Pairing with the test-only code, posting the first shared tray-capture v4 fixture window
  with current timing and paired identifiers, and reading persisted
  documents through the `GET /__test/artifacts` helper route added for privacy checks
- Running the privacy scanner on the captured upload request, persisted `window` payloads, and
  decoded INFO audit records collected during the flow

Limits (not verified by this path):

- No TLS termination or production MongoDB Atlas persistence
- The capture uploads one monitoring window; enrollment collections are returned empty
- No live Rust tray binary or WSS session; this replays the HTTP upload path only
- Ignored Rust `live_*` tests still require a manual test server and real agent for full transport
  coverage
## Rust agent traffic capture (#157)

`scripts/agent_link_test_server.py` can record what the agent sends: with
`INQUISITOR_CAPTURE=<file>` it appends every agent HTTP request (method, path, raw body; the
`Authorization` header is never recorded) and every agent WebSocket message, before the server
parses it. [`scripts/check_agent_traffic.py`](../scripts/check_agent_traffic.py) then fails on
anything outside the protocol: socket messages may only carry `v`, `type`, `paused`, and
`agent_version`; pairing sends only `code` and `name`; uploads must pass `validate_window`
(schema v4 aggregates, no extra fields); heartbeats carry no body.

Recorded run (2026-11-15): the three Rust `live_*` tests, which use the real link worker and
WinHTTP client, against the capturing server. 18 records: 3 pairing requests, 7 window uploads,
and 8 socket messages. Result: `agent traffic check: ok`. No characters, key names, key codes,
window titles, URLs, or event sequences appeared.

Limits: the windows are synthetic test windows, not real typing; the server was local plain HTTP,
so this does not cover TLS or the deployed host; the capture is taken at the receiving application
after HTTP and WebSocket framing are decoded, not by an intercepting proxy.
